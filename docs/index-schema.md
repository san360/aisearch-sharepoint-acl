# Index schema: what every field is for

Definition: [`scripts/search/index.json`](../scripts/search/index.json) (REST API `2026-08-01-preview`). Each search
document is one **chunk** of a SharePoint file (~2,000 characters, 300 overlap). The skillset's index projections
([`skillset.json`](../scripts/search/skillset.json)) copy the file's metadata — including its permissions — onto every
chunk, and the parent file itself isn't indexed (`projectionMode: skipIndexingParentDocuments`).

## Index-level settings

| Setting | Value | Significance |
|---|---|---|
| `permissionFilterOption` | `enabled` | Turns on query-time ACL trimming. When a query carries `x-ms-query-source-authorization`, Azure AI Search filters on the fields marked `permissionFilter`. `disabled` stores the ACLs but ignores them |
| `sharePointConnectorAppRegistration` | `applicationId` = ingestion app, `federatedCredentialId` = search UAMI client ID, `tenantId` | Lets the search service call SharePoint **as the searching user** to find their SharePoint site group memberships at query time. Without it, `spg:` entries never match and SharePoint-group access (Bob → Finance) is lost. See [federated-identity.md](federated-identity.md) |
| `semantic` | `semantic-config`: title = `title`, content = `chunk` | Semantic ranker, captions and answers |
| `vectorSearch` | HNSW, cosine; vectorizer `aoai-vectorizer` (`text-embedding-3-large`, managed identity) | Vector and hybrid queries; the vectorizer embeds the query text at query time, so the app sends plain text |

## Fields

ACL column: **●** = used for permission trimming, **○** = supports it.

| Field | Type | Attributes | Filled from | ACL | Purpose |
|---|---|---|---|:-:|---|
| `chunk_id` | String | **key**, searchable (`keyword` analyzer), sortable | generated by the projection | | Unique chunk ID. Index projections require a searchable key with the `keyword` analyzer |
| `parent_id` | String | filterable | parent document key | | Groups the chunks of one file (`parent_id eq '…'`), used for deletion and change tracking |
| `title` | String | searchable (`en.microsoft`), filterable, sortable | `metadata_spo_item_name` | | File name; semantic title field |
| `url` | String | retrievable | `metadata_spo_item_weburi` | | Link to the file in SharePoint (opens with the user's own SharePoint session) |
| `metadata_spo_item_path` | String | filterable, facetable | `metadata_spo_item_path` | | Drive-relative path (`/drives/<id>/root:/Quantum/…`). The app derives the folder from it; facetable for "by folder" counts |
| `site` | String | filterable, facetable | `metadata_spo_site_url` | | Site URL for faceting/filtering in the UI. A copy of `SharePointSiteUrl`, because that field can't be facetable |
| `last_modified` | DateTimeOffset | filterable, sortable | `metadata_spo_item_last_modified` | | Freshness, sorting |
| `chunk` | String | searchable (`en.microsoft`) | split skill page | | The text: keyword (BM25) search, highlights, semantic content, RAG grounding |
| `chunk_vector` | Collection(Single), 3072 | searchable, **not retrievable, not stored** | embedding skill | | Vector of `chunk` for vector/hybrid search. See [below](#why-chunk_vector-isnt-retrievable) |
| `UserIds` | Collection(String) | `permissionFilter: userIds`, filterable | `metadata_user_ids` | ● | Entra **user object IDs** that SharePoint grants access to the file directly |
| `GroupIds` | Collection(String) | `permissionFilter: groupIds`, filterable | `metadata_group_ids` | ● | Entra **group object IDs** plus SharePoint **site groups** as `spg:<site-collection URL>:<group id>` |
| `SharePointSiteUrl` | String | `sharepointSiteUrl: true`, filterable | `metadata_spo_site_url` | ○ | Tells the query engine which site collection to ask about `spg:` membership. Always the **site collection** URL — also for subsite items, because SharePoint groups are site-collection scoped |

### The three ACL fields

At query time Azure AI Search takes the user's token from `x-ms-query-source-authorization` and computes:

* the user's **object ID** → matched against `UserIds`;
* the user's **Entra groups** (transitive) → matched against `GroupIds`;
* for each `SharePointSiteUrl` in the candidates, the user's **SharePoint site groups** (via
  `sharePointConnectorAppRegistration`) → matched against the `spg:` values in `GroupIds`.

A chunk is returned if **any** of them matches (`UserIds` ∩ {user} ∪ `GroupIds` ∩ {groups} ≠ ∅). The filter runs inside
the engine before ranking, so trimmed chunks never influence scores, captions or answers. The app doesn't add any
`$filter`.

Two special values exist: `"all"` (any user matches) and `"none"` (same as an empty list). The SharePoint indexer never
writes them, so finding `"all"` in this index means someone wrote it directly — see
[index-integrity.md](index-integrity.md).

The ingested values are SharePoint's **effective** permissions on the item: site-level permissions when the folder
inherits, the unique permissions when it doesn't. Sharing links, "Everyone" claims and guests aren't supported
([limitations.md](limitations.md)).

### What's actually in the index (elevated read)

Read with `x-ms-enable-elevated-read: true` (admin token, *Search Index Data Contributor*). Names replace the GUIDs; on
both sites SharePoint group **3** = Owners, **4** = Visitors, **5** = Members.

| Codeword · location | Folder permissions | `UserIds` | `GroupIds` | Who gets it |
|---|---|---|---|---|
| BLUEBIRD · Research / Public | inherits site | admin | All staff · `spg:…research:3,4,5` | Alice, Bob, Carol (All staff) |
| AURORA · Research / Quantum | unique | admin | Quantum team · `spg:…research:3` | Alice (Quantum team) |
| KESTREL · Research / Bio | unique | admin · **Carol** | `spg:…research:3` | Carol (direct) |
| WREN · Research › Archive library / Notes | inherits site | admin | All staff · `spg:…research:3,4,5` | Alice, Bob, Carol |
| HERON · Research › LLM Lab subsite / Papers | inherits subsite (unique) | admin · **Bob** | Quantum team · `spg:…research:3` | Alice (Quantum team), Bob (direct) |
| MAGPIE · Research › LLM Lab subsite / Drafts | unique | admin · **Bob** | `spg:…research:3` | Bob (direct) |

| OSPREY · HR / Confidential | — | not indexed | — | nobody (no `Sites.Selected` grant) |

* **admin** is the deploying admin, who created the sites and is their site collection administrator; **Owners (3)** keep

* Bob's Finance access exists **only** as `spg:…finance:5` — the proof that SharePoint site groups are resolved at query time.

### Why `chunk_vector` isn't retrievable

It's deliberate: `"retrievable": false, "stored": false`.

* The vector is only needed **inside** the engine for similarity matching (the HNSW graph). Returning 3,072 floats
  per result (~30 KB of JSON) would bloat every response and is useless to the UI or the LLM, which use `chunk`.
* `stored: false` drops the extra stored copy of the vector that exists only to be returned, which reduces storage
  (the portal's *Total storage*); the vector index (*Vector index quota usage*) is unaffected and search works the same.
* Trade-off: `stored` can't be changed later. To ever return vectors (for example, to export them), the index must be
  rebuilt with `stored: true`; `retrievable` can then be toggled freely.

### Why `UserIds` / `GroupIds` are retrievable here

The documentation recommends `retrievable: false` for the ACL fields in production and `true` only while verifying. This
demo keeps them retrievable so the admin views (live matrix, raw JSON, "who can see this chunk") can show them. A normal
query returns only chunks the user may read anyway, but it could still reveal the IDs of other people who share access.
For production, set `retrievable: false` — that change doesn't need an index rebuild.
